- 27 Oct 2026, Phase 2 BUILT: `src/compare/` — `align.py` (distance-rescales two laps to a shared reference length, resamples to a 1m grid, computes the cumulative delta-time curve; brake stays boolean/nearest-sample, never interpolated), `segments.py` (one segment per corner, boundaries at the MIDPOINT between consecutive corners — not at the corner markers themselves, which would clip either the braking or exit phase; measures time delta, braking-point diff, min-speed diff, throttle-pickup diff, exit-speed diff, top-speed diff per segment and classifies the dominant cause), `insights.py` (templated plain-English summaries ranked by time lost, no LLM), `loader.py` (resolves "fastest" or a specific lap number to telemetry — fastest laps are already in the store from Phase 1; anything else is fetched live from FastF1 and lazily cached into the same Parquet partition), `service.py` (orchestrates the whole pipeline + mini-sector winners for the track map). New endpoint `GET /compare_laps?session_id=&driver_a=&driver_b=&lap_a=&lap_b=&resolution=`, store-backed and driver-pair-agnostic — sits alongside the old `/compare/qualifying` (live FastF1, fastest-lap-only, pre-store), which is untouched. Verified against real data: Bahrain 2022 Q LEC vs VER through the new endpoint gives `total_delta_s = 0.123s`, matching the old endpoint's number exactly; the lazy-cache path (a non-fastest lap) was fetched live then confirmed to hit cache (0.11s) on the second call; 404s confirmed for unknown driver/session. Caught and fixed two real bugs along the way: (1) DuckDB's Python connection leaves a result "unfinished" after `.fetchone()`, breaking the *next* `execute()`/`register()` call on that connection — hit this for real mid-backfill (crashed on every season's 2nd event); switched `is_ingested` to `.fetchall()`. (2) `write_telemetry_parquet`'s `file_stem` param (added to disambiguate a non-fastest lap's filename) was also being used as the stored `driver_id` *content*, silently breaking every `WHERE driver_id = ?` query for that lap — decoupled filename from content, added a regression test (`tests/test_store_telemetry_naming.py`). Also confirmed empirically: DuckDB on this Windows setup does NOT support a read-only reader while a separate process holds a write connection open (`db.connect(read_only=True)` added anyway, for when ingestion isn't running concurrently with the API — which, for now, it can't be). 15 new tests (`test_align.py`, `test_segments.py`, `test_store_telemetry_naming.py`), 28 total passing.
- 27 Oct 2026, user-requested feature BUILT (ahead of Phase 3, same session as Phase 2): whole-race lap-by-lap gap evolution between two drivers — `src/compare/race.py` + `GET /compare_race?session_id=&driver_a=&driver_b=`. Cumulative race-time gap per lap (a broadcast "race trace" chart; pit-stop time counts, since it's real elapsed time), pit laps, tyre stints (compound + pace, pit in/out laps excluded from the pace average), and exactly which laps the on-track order flipped (`lead_changes`, sign-of-gap-change detection). Confirms Hamilton caught and passed Verstappen late (lead change detected at lap 67, right before Verstappen's final stop at lap 68) — the data backs the story. 7 new tests (`tests/test_race.py`), 35 total passing. ## Known limitations found during exploration

- F1's live-timing service returns HTTP 401 without an F1TV subscription (tested 26 Oct 2026). The existing cache still works; nothing new can be downloaded with FastF1 3.8.3.
- The race engine replays each race's real pit laps, compounds and in/out-lap times, and never retires a car. The qualifying predictor uses the real best quali lap and race grid. Both are reconstructions of known sessions, not forecasts.
- Models are per circuit (10 circuits), trained 2022-2024 with label-encoded drivers and teams; they cannot score unseen drivers, teams or circuits.
- Model validation uses random 5-fold CV over laps, which mixes laps from the same race into train and test.
- No tests. The project root is not a git repository (only `web/` is).
- The project sits in OneDrive; the Next.js dev server already stalls on OneDrive-synced `node_modules`.
