## Known limitations found during exploration

- F1's live-timing service returns HTTP 401 without an F1TV subscription (tested 26 Oct 2026). The existing cache still works; nothing new can be downloaded with FastF1 3.8.3.
- The race engine replays each race's real pit laps, compounds and in/out-lap times, and never retires a car. The qualifying predictor uses the real best quali lap and race grid. Both are reconstructions of known sessions, not forecasts.
- Models are per circuit (10 circuits), trained 2022-2024 with label-encoded drivers and teams; they cannot score unseen drivers, teams or circuits.
- Model validation uses random 5-fold CV over laps, which mixes laps from the same race into train and test.
- No tests. The project root is not a git repository (only `web/` is).
- The project sits in OneDrive; the Next.js dev server already stalls on OneDrive-synced `node_modules`.

- 28 Oct 2026, Phase 4 STARTED (per PLAN.md section 7, D1): the restructuring's foundational piece — rolling pace features that replace the old engine's per-circuit LabelEncoded identities, which is what let `/predict/*` only ever know 10 circuits and 2022-2024. `src/forecast/schedule.py` (chronological event calendar 2018-2026 straight from FastF1, independent of the store's partial backfill — `events_before()` is the leakage boundary every walk-forward step must respect) and `src/forecast/pace.py`: `session_pace()` computes each driver's median clean lap, gap to that session's fastest (team-lineage-mapped via `src.store.ids.team_lineage_id` so a rebrand like Sauber->Audi doesn't reset a team's history), and gap to their own teammate; `build_pace_history()` stacks this over a chronological event list; `rolling_pace_asof()` turns the long history into an "as of this event" feature via a shift(1)-then-EWM per group — shift(1) is the leakage guard, so the event being forecast never contributes to its own feature. Caught and fixed a real bug before it reached the model: the team-level rolling average was computed per DRIVER-ROW rather than per TEAM-ROUND, so two teammates at the same round could see different "team pace" values (each one's immediate predecessor row was 50% of the time the OTHER driver's same-round result, not the team's own prior round) — fixed by aggregating to one row per team per round first, then rolling that, then merging back onto both drivers. Added a regression test for exactly this (`test_teammates_share_the_same_team_asof_value`). Verified against real 2024 data: `session_pace(2024, 1, "R")` reproduces the known Bahrain pecking order exactly (VER fastest, Red Bull/Ferrari at the front, backmarkers correctly last); a 3-round rolling sweep confirms both Mercedes/Ferrari/Red Bull drivers now share one team number per round and that number uses strictly prior rounds only. 6 new tests (`tests/test_forecast_pace.py`, synthetic data, no network — same convention as the rest of the suite), 42 total passing. - 29 Oct 2026, "first set" race model RESULT: first full run (default hidden=(128,64,32), lr=1e-3, batch=4096) gave 2025-eval RMSE 7.58s/MAE 6.47s -- better than the 10.2s do-nothing baseline (so the pipeline works and is learning real signal), but worse than the old per-circuit XGBoost models (0.9-3.5s on their own circuits) and worse than a reasonable target. Diagnosis from the epoch log: best internal validation score was EPOCH 1, every epoch after was worse -- the network had too much capacity for 12 continuous features + 2 small categoricals and started overfitting almost immediately. Retuned (hidden=(64,32), dropout 0.2->0.35, weight_decay 1e-4->1e-3, lr 1e-3->3e-4, batch 4096->1024, patience 8->20/epochs 80->150, now the defaults in `train_nn.py`/`nn_model.py`) and reran: RMSE 4.37s (seed 42), then RMSE 3.45s/MAE 2.85s on a second seed (7) to confirm it wasn't a lucky split -- both far better than the first run and now in the same range as the OLD specialized per-circuit models, despite this being one model covering every circuit at once (strictly a harder task). Both runs showed internal validation getting WORSE than the final true-2025 number (e.g. val 6.12s vs eval 3.45s) -- counterintuitive at first glance, but explained by the internal validation split being only ~10 held-out events from 3 seasons, so one awkward race skews it, while the real 2025 eval averages over a full 22-race season.
